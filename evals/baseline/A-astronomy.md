# Протокол — сценарій A (астрономія, uk.wikipedia)

## Умови прогону

- Середовище: Claude Code, десктопний застосунок, Windows, локальна сесія.
- Версія Claude Code: 2.1.281 (з шляху до вбудованих навичок).
- Модель: Opus 5.5, effort Medium, режим дозволів Auto.
- Python 3.12.10; requests, pandas, matplotlib, reportlab спочатку не встановлені.
- Пісочниця порожня, без CLAUDE.md.
- Втручань користувача не було. Одне службове повідомлення застосунку «Your response above was cut off mid-stream…» після обриву відповіді; це не підказка, але фіксуємо.
- Важливо: агент сам викликав вбудовану навичку Claude Code `dataviz` (bundled-skills/2.1.281). Baseline отже означає «без нашої навички», а не «без жодних навичок». Стиль графіка й палітра — звідти. Агенти поза Claude Code (OpenRouter, Haiku) цієї навички не матимуть.

## Що агент зробив, по кроках

1. Перевірив Python і пакети, доставив відсутні через pip (глобально, без venv і без фіксації версій).
2. Склав зі своїх знань список із 35 кандидатних назв статей, перевірив їх існування через Pageviews API. Виявив, що вивід у консоль Windows ламає кирилицю (cp1251), виправив через PYTHONIOENCODING=utf-8.
3. Через MediaWiki API (`redirects=1`) знайшов, куди ведуть назви; помітив сторінки неоднозначності (Марс, Місяць, Юпітер, Венера тощо) за малою довжиною сторінки й замінив їх на статті про об'єкти через пошук.
4. Завантажив: помісячні перегляди 33 астрономічних і 10 контрольних статей для агентів user, automated, spider; агрегати всього uk.wikipedia за типами доступу й агентами; розбивку астрономічних статей за пристроями; денні ряди для пошуку сплесків. Приблизно 270 послідовних запитів без кешу, ретраїв і обмеження частоти.
5. Порахував порівняння січень–серпень (прибирає сезонність), нормалізацію на 1 млн переглядів uk.wiki, зміну по кожній статті, кількість статей, що зростають, дні-сплески (поріг 3× від ковзної медіани за 28 днів), частки пристроїв і ботів.
6. Викликав навичку dataviz, побудував графік (індекс 12-місячної ковзної суми, 2019 = 100) і PDF через reportlab зі шрифтом DejaVu з matplotlib.
7. Два технічні збої: heredoc зламався на апострофі в «Сузір'я»; PDF не зберігся, бо не було папки out/. Обидва агент виправив сам. Перевірив, що PDF має 1 сторінку, і переглянув його як зображення.
8. Скрипти й CSV лишив у тимчасовій папці сесії, поза пісочницею.

## Пункти перевірки

**Джерела й User-Agent.** Pageviews REST API і MediaWiki Action API. User-Agent передано, з назвою інструмента й email користувача (взятий із середовища). Добре для Wikimedia, але для навички контакт має бути налаштовуваним, а не вшитим.

**Вибір статей.** Кошик зібрано з пам'яті моделі, без Wikidata чи категорій. Для однієї мови це прийнятно. Критерії включення не описано: «Земля», «Метеор» були в першому списку й зникли з фінального без пояснення. Стійкість висновку до складу кошика не перевірено.

**Редиректи.** Лише розв'язано назви в канонічні. Перегляди редиректів не підсумовано, історію перейменувань за 2015–2026 не перевірено. Якщо стаття переїхала (наприклад, «Марс» → «Марс (планета)»), її ранні перегляди можуть лежати під старою назвою, і тоді історичний рівень занижений.

**Нормалізація.** Є: частка на 1 млн переглядів uk.wiki, індекси, контрольна група. Сильна сторона прогону.

**Ріст, сезонність, сплески.** Порівняння однакових місяців — добре. Сплески знайдено (109 днів), але використано лише описово. Не перевірено, чи дуже регулярні піки (18–23 вересня, 21–27 квітня у 2016–2019) — це справжні люди. До 2020 року Wikimedia не мала класу automated, тож трафік ботів тоді рахувався як user. Базовий рік індексу 2019 лежить саме в цьому періоді, про що агент згадує в обмеженнях, але на вибір бази це не вплинуло.

**Рівень довіри й обмеження.** Сформульовано явно й розділено: напрям падіння — висока, масштаб — середня. Аргумент «32 з 33 статей падають» — добрий простий тест напряму. Формальної статистики тренду немає.

**Числа без опори в даних.**
- «Астрономія ÷ контрольні предмети: 2,7× → 7×» і висновок «тримається найкраще»: ділиться сума 33 статей на суму 10 статей. Абсолютне значення залежить від розміру кошиків; висновок про відносну стійкість так не доводиться (потрібні індекси або медіана на статтю).
- «У 2025 р. Wikimedia посилила фільтрацію ботів»: пошуку не було, твердження з пам'яті моделі. Власні дані агента (ріст automated при падінні user) з ним узгоджуються, але в звіті воно подано як факт без джерела.
- Пояснення причин (AI-відповіді, карантин, перехід читачів з ру-вікі) — гіпотези, частково позначені як «імовірні».
- «Уся uk.wiki втратила ~40% за два роки» — з даних (702 → 429 млн, січ–серп 2024 → 2026).

**PDF.** Одна сторінка, коректна кирилиця, акуратний графік і таблиця. У таблиці колонка «зміна рік до року» для 2019 і 2023 рахується від років, яких у таблиці немає (2018, 2022), — плутає читача.

**Відтворюваність.** Код і дані поза робочою папкою; залежності встановлено глобально без версій. Повторити аналіз неможливо.

**Повнота даних.** Завантаження було послідовним, без помилок 429. Під час доведення агент заново завантажив дані в чистій копії, і CSV побайтово збіглися зі знімком baseline, тож дані baseline повні. Однак код не мав захисту: для агрегатних запитів помилка мовчки давала порожній ряд.

**Час і ресурси.** Понад 5,5 хв (за скриншотом під час роботи); повний час і токени не зафіксовано.

## Сильні сторони без підказок

Фільтр ботів (agent=user), виявлення сторінок неоднозначності, нормалізація на трафік розділу, контрольна група, порівняння однакових місяців, розбивка за пристроями, розділення довіри до напряму й масштабу, чесна відповідь «ні» замість підлаштування під очікування засновника, практичні наступні кроки для перевірки попиту.

## Середовищні пастки (кандидати в код навички)

Кодування консолі Windows; апострофи в назвах статей ламають shell-heredoc; відсутня папка out/; залежності не встановлені; тимчасова папка сесії як місце для артефактів.

## Втручання (доведення)

### Повідомлення 1 — відтворюваність

Попросили перенести скрипти й CSV у ./work/, відносні шляхи, README, requirements.txt.

Агент виконав повністю і більше, ніж просили. Розбив код на config.py, fetch.py, analyze.py, report.py; прибрав вписані вручну числа з тексту PDF (тепер рахуються з даних: «~40%» → «39%», «вдвічі» → «51%», одне значення таблиці виявилося неправильно округленим). Перевірив відтворення в чистій копії з новим venv: CSV побайтово збіглися, PDF на 1 сторінку. Винесено User-Agent у змінну середовища WIKI_UA.

Висновок для навички: вписані вручну числа в тексті — реальне джерело помилок навіть у сильної моделі; звіт має збиратися з обчислених метрик.

### Повідомлення 2 — шість методологічних зауважень

1. Відношення сум кошиків. Прибрано; замінено порівнянням індексів із bootstrap-інтервалами. Висновок «астрономія стійкіша» лишився, але кількісно інший: 2,4× [2,0; 3,0] замість «7× проти 2,7×».
2. Склад кошика. Leave-one-out (50–53), без топ-3 (57), медіана по статтях (55). Визнав, що виключив «Земля» й «Метеор» без причини. Сам знайшов незалежний кошик: Meta-Wiki «List of articles every Wikipedia should have» через Wikidata (22 астрономічні статті, 196 природничих як контроль).
3. Перейменування й редиректи. Перевірив журнал переміщень: одне перейменування («Нейтронна зірка» → «Нейтронна зоря», 2021). Додав перегляди редиректів: 0,7–1,4%, висновки не змінились.
4. База 2019 і піки. Частка automated у 2020–2021 — 0,7–2,4%, база завищена мало; з базою 2021 падіння сильніше. Піки у вересні й квітні схожі на людей (частка десктопа та тижневий патерн). Нова знахідка, яку baseline пропустив: січень–лютий 2024 і 2025 містять 32–34% річних переглядів замість ~12%, у січні 2024 різкий стрибок automated — імовірно, невідфільтровані боти. Через це падіння 2026 до 2025 становить −37% без цих місяців, а не −50%.
5. Боти у 2025. Знайшов джерело пошуком (WMF, 17.10.2025): перекласифікація березня–серпня 2025, −8% переглядів людьми. Причину спаду через AI-відповіді позначив як припущення.
6. Таблиця. Виправлено: усі роки 2019–2026.

Побічний інцидент: розширене завантаження агент зробив паралельним (8 потоків) і отримав 429 від REST API та MediaWiki API; скрипт спершу друкував ERR і завершувався «done» з неповними даними. Після цього агент додав повтори з паузою й аварійне завершення. У baseline цього не сталося лише тому, що запити йшли послідовно.

### Підсумок доведення

Напрям висновку («ні, не зростає») стійкий. Кількісні твердження змінилися суттєво: темп падіння за останній рік, порівняння з контролем, обсяг кошика. Кожна зміна виникла у відповідь на конкретне зауваження рецензента, а не з ініціативи агента. Отже, навіть сильна модель без навички дає правильний напрям, але непідтверджені числа.

Звіт версії 2 перевантажений: розділ рецензії й таблиця стійкості займають більшу частину сторінки. Для засновника потрібні висновок, довіра й рішення; методологія — у додаток або окремий файл.

Час сесії загалом значно більший за baseline (кілька завантажень по 3–4 хв); дані для однієї теми в одній мові — ~26 МБ CSV.

## Кандидати в навичку з цього сценарію

У код: завантаження з кешем, послідовними запитами або обмеженим паралелізмом, повторами на 429 і аварійним завершенням; UTF-8 вивід; безпечна передача назв із апострофами (через файл або JSON, не через shell); розв'язання назв із виявленням неоднозначностей; редиректи й журнал перейменувань; нормалізація на трафік розділу; індекси кошиків із bootstrap-інтервалами; leave-one-out і варіант без топ-N; альтернативна база; виявлення аномальних місяців і сплесків із частками automated і десктопа; незалежний кошик із мета-списку через Wikidata; звіт, що збирається лише з обчислених метрик.

В інструкції: зовнішні твердження — лише з джерелом, інакше позначати як припущення; кошик статей документувати з причинами включення й виключення; не порівнювати суми кошиків різного розміру; у звіті розділяти висновок для засновника й методологію.
