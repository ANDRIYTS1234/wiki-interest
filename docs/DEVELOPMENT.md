# Як розроблялась навичка і як перевірявся результат AI

## Процес коротко

1. **Baseline без навички.** Три реальні запити засновника (A — астрономія, uk; B — інтервальне голодування, pl vs cs; D — шахи, de/es/pt з хибною передумовою) виконано сильною моделлю (Claude Opus 5.5, Claude Code, effort Medium) у порожніх пісочницях без жодних підказок. Потім кожну відповідь перевірено як рецензент і дано агенту зауваження; усе, що довелося підказати, записано. Протоколи: `evals/baseline/`.
2. **Специфікація коду** (`docs/SPEC.md`) виведена з протоколів: кожна вимога закриває конкретний провал. Ключове рішення: усе, що має одну правильну відповідь (запити до API, кеш, редиректи, метрики, перевірки стійкості, графіки, верстка), робить код, а не модель. Агенту лишається сформулювати запит, погодити кошик статей і написати висновок — і навіть там числа лише через плейсхолдери з `metrics.json`. Це й робить навичку придатною для дешевої моделі.
3. **Код** написано агентом Claude Code (Opus 5.5) етапами: каркас → resolve → fetch → analyze → report → приклади, CI. Після кожного етапу агент зупинявся; результат перевірявся незалежно (нижче), рішення щодо контракту ухвалювала людина.
4. **SKILL.md і `references/`** написано паралельно з кодом на основі протоколів і погодженого контракту CLI, потім звірено з реальним кодом; розбіжності ловить тест.
5. **Критерії порівняння «без навички / з навичкою»** — `evals/scenarios.yaml`: сценарії A, B, D з baseline, а також C (кілька мов із рекомендацією аудиторій) і E (повторний запит зі зміною припущень).
6. **Прогони на Haiku 4.5 з навичкою** (Claude Code desktop, живі дані, файли в `evals/runs/haiku/`) — докладно в розділі «Прогони навички на Haiku 4.5» нижче:
   - **A до правила «навичка не виконується сама»:** Haiku знайшла навичку, але не запустила жодної команди й підробила звіт — вписані числа, висновок «тренд позитивний, курс додавати». Критичні перевірки: 0 з 7.
   - **A з навичкою (явний виклик):** повний ланцюжок `doctor → resolve → fetch → analyze → report`, відповідь «ні, інтерес падає» (`index_norm` 0,54×), числа лише з метрик, PDF на одну сторінку. Критичні: 3 з 7; провалено склад кошика (A7, A8).
   - **B з навичкою (явний виклик):** відсутність польської статті встановлено через Wikidata й названо прогалиною Вікіпедії, без замінника й прямого порівняння непорівнянного; мови порівняно на спільних QID. Критичні: 4 з 6; висновок «однаковий спад» хибний (B5) через малий кошик і ваду в коді, яку цей прогін і знайшов (перекриття вікна з базою: після виправлення pl −32%, cs −25% замість −16% і −15%).
   - Усі сім знахідок цих прогонів виправлено в коді й SKILL.md з тестами; повторні прогони ще попереду.

## Що показав baseline

У всіх трьох сценаріях модель без навички правильно визначила напрям («інтерес не зростає»), але кількісні висновки виявились хибними, а у B і D після методичної перевірки розвернулася навіть рекомендація, на який ринок іти.

| Провал без навички | Де | Наслідок | Що закриває |
|---|---|---|---|
| Редирект узято замість статті («Reglas del ajedrez» замість «Leyes del ajedrez») | D | «Навчальний попит мізерний» — хибно, у сотні разів | `resolve`: статус `redirect_resolved`; `fetch` підсумовує редиректи |
| Відсутню статтю мовчки замінено іншою («Schachbrett») | D | Аналіз не того, про що питали | `resolve`: явний `missing`, пошукові збіги позначено як нееквівалентні |
| Висновок про тему з однієї статті | B, D | Протилежне порівняння ринків (B), хибна рекомендація ES замість DE (D) | Кошики за Wikidata, панель статей, групи |
| Неперевірені аномальні місяці / сплески | A, B | −50% замість −37% (A); −54% замість −43% (B) | `analyze`: аномальні місяці, сплески з часткою ботів, варіанти без них |
| Порівняння сум кошиків різного розміру | A | «7× проти 2,7×» замість 2,4× [2,0; 3,0] | Індекси кошиків, `compare.*` |
| Статті, створені посеред періоду | D | «Зростання від нуля» | Панель статей, що існують з базового періоду |
| Не підсумовано редиректи й перейменування | A | Занижений історичний рівень | `resolve` збирає редиректи й журнал перейменувань, `fetch` додає їхні перегляди |
| Вписані вручну числа, розбіжність тексту й таблиці | A, D | Помилки округлення, суперечливі формулювання | `report`: числа лише через плейсхолдери, валідатор |
| Необроблені 429, неповні дані без помилки | B, D | Тиха втрата даних | HTTP-шар із повторами, код виходу 5, `--allow-partial` |
| Апостроф у «Сузір'я» ламав shell | A | Збій скрипта | Назви статей лише через JSON-файли |
| Непослідовність між прогонами (верстка, де лежать скрипти) | A, B, D | Невідтворюваність | Фіксований CLI, шаблон звіту, `uv.lock` |

## Як перевірявся результат AI-агента

### Незалежна перевірка кожного етапу

Кожен етап агента перевірявся незалежно від його звіту; повний журнал — `evals/verification-log.md`:

- власноруч запускались `git log`, `pytest`, `doctor`, `git status` — звірка заявленого з фактичним;
- для resolve і fetch — кейси, **яких не було у фікстурах агента** (напр., pt «Regras do xadrez» → має бути редирект на «Leis do xadrez»), щоб перевірити загальну поведінку, а не лише записані приклади;
- для analyze — порівняння з результатами ручного доведення baseline на тих самих сценаріях.

Знайдені розбіжності (приклади): етап не запушено, хоча заявлено; `--dry-run` занижував нижню межу запитів для нерозв'язаних позицій; «168 тестів» у звіті сесії, коли один тест пропускався скрізь (`pyyaml` не було в тестовому середовищі); одна хибна тривога з нашого боку («leis doxadrez» — артефакт копіювання з терміналу), яку агент коректно спростував.

Агент сам знайшов на реальному API речі, яких не було в специфікації: алфавітний порядок посилань на сторінках неоднозначності (серед перших десяти «Марс» не було планети); падіння всього пакетного запиту Wikidata через один неіснуючий QID; «фальшиві нулі» класу automated до 29.04.2020; вплив контакту в User-Agent на швидкість (без контакту ~4× повільніше і часті 429). Кожна знахідка закрита кодом і регресійним тестом.

### Автоматичні перевірки

- **Тести на записаних відповідях справжнього API.** `tests/record_fixtures.py` записує реальні відповіді Wikidata / MediaWiki / Pageviews; тести проганяють код на них без мережі. Закріплені регресійні кейси з baseline: uk «Марс» — сторінка неоднозначності; pl інтервальне голодування — статті немає; es «Reglas del ajedrez» — редирект на «Leyes del ajedrez»; uk «Нейтронна зірка» → «Нейтронна зоря» (перейменування 2021).
- **Синтетичні ряди з відомою відповіддю** для метрик: геометричний індекс, bootstrap, leave-one-out, детектор сплесків, аномальні місяці, нормалізація, формат чисел uk.
- **Детермінованість:** однакові вхідні дані дають побайтово однаковий `metrics.json`.
- **Офлайн end-to-end** (`tests/test_e2e_offline.py`): `analyze → report` на знімку кешу сценарію B, будь-який мережевий виклик валить тест, PDF рівно на одну сторінку.
- **CI** (GitHub Actions): ubuntu / windows / macos × Python 3.10 / 3.12, `uv sync --locked`, усі тести, `doctor` з іншої папки.
- **Синхронність документації з кодом** (`tests/test_skill_docs.py`): коди прапорців і їхні формулювання в `references/interpreting.md` дослівно збігаються з тим, що друкує PDF; приклади плейсхолдерів мають правильні формати; frontmatter SKILL.md — валідний YAML у межах лімітів.

### Ручні перевірки

- **Артефакти.** PDF прикладу B переглянуто очима: одна сторінка, кирилиця й польська діакритика, усі прапорці в застереженнях.
- **Прохід SKILL.md як агент** у порожній папці з навмисно зламаним входом (вписане число, невідомий шлях, задовгий текст, неправильний формат). Знайдено баг: валідатор приймав `{…index_norm:pct}`, що надрукувало б індекс 0,85 як «+85%»; тепер для відношень вимагається `:x`, для змін — `:pct`.
- **Валідатори формату навички:** `agentskills validate` (відкритий стандарт) — валідно; `claude plugin validate` — «Validation passed».

## Прогони навички на Haiku 4.5

### Сценарій B, офлайн-кеш

Механічно все спрацювало: правильний `analysis.json` з позначеним замінником, `fetch` без мережевих запитів, PDF на одну сторінку; валідатор відхилив вписане число й задовгий текст, модель виправила їх сама; на повторному запиті змінено `analysis.json` і перезапущено аналіз з кешу. Три змістові провали перенесено з тексту SKILL.md у код (коміт `49022ad`, тести в `tests/test_e2e_offline.py`):

| Провал Haiku | Що тепер робить код |
|---|---|
| Порівняла польський замінник з чеською статтею напряму | `analyze` позначає пару `comparable: false` з причиною (яка стаття відсутня, який замінник) і пише в stdout `DO NOT COMPARE DIRECTLY — …`; PDF друкує той самий рядок |
| Згадала в PDF не всі прапорці якості | PDF завжди друкує всі прапорці людськими формулюваннями, незалежно від тексту агента; при нестачі місця — компактна верстка, а не пропуск |
| Повторний запит міг створити другий звіт поруч | `report` за замовчуванням пише в той самий `<workdir>/report.pdf` і повідомляє `"replaced": true`; невдалий повторний запуск не знищує попередній звіт |

### Сценарій A, Claude Code desktop, навичку не згадано в запиті

Haiku відкрила навичку, але вирішила, що навичка «працює сама» й чекала результату; далі не запустила жодної команди CLI, а написала власний `generate_report.py` зі вписаними числами («~2,400», «+12–18%») і висновком «тренд позитивний, курс додавати можна» — протилежним до `analyze` на реальних даних (−35%). У підписі звіту стояло «Джерело: Wikipedia Pageviews API», кирилиця в PDF вийшла квадратами. Виправлено в SKILL.md (коміт `ee4cf3f`): перше речення тіла — «навичка не виконується сама, запускай команди сам, починаючи з `doctor`»; перше правило — жодних чисел і висновків без виконаних `resolve → fetch → analyze → report`, жодних власних скриптів; якщо команди не працюють — зупинитися й сказати користувачу. Обидва речення стережуть тести.

У тому ж прогоні Haiku знайшла тимчасову копію навички з тесту спрацювання (див. нижче) — це й виявило ваду вимірювального інструмента.

### Сценарії A і B, Claude Code desktop, явний виклик навички

Навичка лежала в `.claude/skills/wiki-interest/` пісочниці (з GitHub, уже з правилом «навичка не виконується сама»), у кінці запиту — «Використай навичку wiki-interest». Транскрипти, специфікації й PDF — `evals/runs/haiku/A-with-skill/` і `B-with-skill/`.

**A.** Haiku пройшла `doctor → resolve → fetch → analyze → report`; відповідь «ні, інтерес падає» (`index_norm` 0,54×), числа лише з метрик, PDF на одну сторінку, прапорці надруковано автоматично — протилежне до діагностичного прогону на тій самій моделі. Слабке місце — кошик: тему розбито на три кошики, target з однієї статті (`PANEL_SMALL`), а «небесні об'єкти» взято як контроль, хоча це теж астрономія, тож висновок «астрономія падає сильніше за контроль» хибний.

**B.** Відсутність польської статті встановлено через Wikidata й прямо названо прогалиною Вікіпедії, а не відсутністю попиту; жодного замінника й прямого порівняння непорівнянних статей (краще за baseline Opus); мови порівняно на кошику тих самих QID. Але висновок «pl −16%, cs −15%, однаковий спад» розійшовся з доведеним Opus («Польща втрачає швидше»): кошик лише з чотирьох статей і — головне — вада в коді, описана нижче.

**Обмеження середовища: навичку не видно за описом.** У прогонах A перелік навичок, який Claude Code дає моделі (`skill_listing` у транскрипті), показав нашу навичку лише назвою — `- wiki-interest`, без опису: у середовищі було ще кілька десятків навичок і плагінів, і Claude Code скоротив описи. Без опису Haiku не має з чого зрозуміти, що навичка підходить до запиту, тому без явної згадки не викликала її. Справа не в тексті опису — його просто не показали; у прогоні B опис у переліку був (ще попередня версія). Звідси порада в README: якщо встановлено багато навичок, викликати wiki-interest явно.

**Що змінено за цими прогонами** (коміти після `e2d98c5`, кожен із тестами):

| Що показав прогін | Що тепер робить навичка |
|---|---|
| A: target з однієї статті, «контроль» — підмножина теми | SKILL.md і `basket-building.md`: target — 5–20 статей самої теми, підтеми — групами всередині нього; control — інша тема. `analyze`: якщо в target менше 3 порівнянних статей — рядок у `attention` і довіра до напряму не вище low (`069ef2e`) |
| B: база перекривала вікно (нижче) | Зсув бази — ціле число років, не менший за вікно; перекриття з `baselines` — помилка вводу; підписи показують реальне порівняння (`8f25943`) |
| Застереження в PDF перелічували технічні шляхи кошиків | Місце прапорця — «усі кошики» або назва кошика; блок застережень не більше чверті сторінки (`1fd6f02`) |
| Бейджі довіри показували `astronomy/uk` | Бейджі показують назву кошика (`1fd6f02`) |
| B: агент дописав у застереження те, що PDF і так друкує | Дубль прапорця не друкується, а потрапляє в `caveats_dropped`; правило в SKILL.md (`1fd6f02`) |
| B: 12 з 14 викликів `report` завершились помилкою — Haiku вгадувала формат плейсхолдерів | Кожна помилка валідатора містить готовий плейсхолдер і виправлене речення; помилки формату JSON — з мінімальним правильним прикладом; при переповненні сторінки названо найдовші поля (`26c9e52`) |
| B: посеред роботи агент перейшов на польську, заголовок і висновки PDF — англійською | SKILL.md: увесь narrative — мовою користувача, `--report-lang` їй відповідає; `report` попереджає в `language_warnings`, якщо текст іншою мовою (`2fe35b9`) |

Після цих змін прогони A і B на Haiku ще не повторювались.

### Ваду в розрахунку знайшов прогін на слабкій моделі

У B Haiku правильно взяла «останні два роки» як вікно 24 місяці. Код тоді порівнював вікно з тими самими 24 місяцями роком раніше, тож рік 09.2024–08.2025 входив і у вікно, і в базу, і спільна частина занижувала зміну. Приклад B у репозиторії теж мав вікно 24 місяці, але ні тести, ні ручні перевірки цього не помітили. Виправлення: база зсувається на `ceil(months / 12)` років — для 12 місяців це попередні 12, для 24 — попередні 24, для 18 — ті самі місяці двома роками раніше; зсув кратний 12, тож сезонність і далі прибрано.

Специфікація Haiku (`evals/runs/haiku/B-with-skill/analysis.json`), ті самі живі дані, до і після виправлення:

| | До (база перекривала вікно) | Після (попередні 24 місяці) |
|---|---|---|
| Кошик суміжних тем, pl | −16% | −32% |
| Кошик суміжних тем, cs | −15% | −25% |
| pl проти cs, ті самі QID | 0,98× [0,90; 1,14] | 0,91× [0,79; 1,14] |
| Чеська стаття про інтервальне голодування | −31% | −61% |

«Однаковий спад» став «Польща втрачає швидше» — той самий напрям, що в доведеного Opus; інтервал поки містить 1, бо в кошику чотири статті.

### Спрацювання навички (description)

Метод: запит без назви навички, `claude -p` на Haiku 4.5; прогін зараховано, якщо перший виклик інструмента — навичка. 8 релевантних і 8 схожих нерелевантних запитів з `evals/triggers.yaml`, по 3 прогони. Сирі результати — `evals/trigger-runs/`.

Перші заміри (skill-creator `run_eval`) дали 6 з 24 для початкового опису і 1 з 24 для «наполегливішого». Під час повторного заміру в інструменті знайдено дві вади: усі паралельні прогони реєстрували свої копії навички в одному проєкті (модель бачила кілька копій під різними іменами, і вибір «чужої» рахувався як промах), а з папки без `.claude/` копія потрапляла в `~/.claude/commands` і ставала видимою для всіх сесій на машині. Тому заміри повторено власним інструментом `evals/trigger_eval.py`: кожен прогін в окремій тимчасовій папці, прибирання за собою, позитивний контроль (запит, що прямо називає навичку).

| Опис | Релевантні (спрацювало) | Нерелевантні (хибні спрацювання) | Позитивний контроль |
|---|---|---|---|
| Початковий | 0 з 24 | 0 з 24 | 1 з 3 |
| Новий (рішення, для яких навичка, ключові слова двома мовами) | 4 з 24 | 0 з 24 | 3 з 3 |

Обидва заміри — на одній машині (Windows, Claude Code 2.1.274, близько тридцяти інших навичок і MCP-інструментів у середовищі). Межу «коли не використовувати» опис тримає; новий опис спрацьовує частіше, але до порогу (понад половина прогонів) дотягує лише один запит з восьми. Найчастіший перший виклик — `ToolSearch` (підвантаження вебпошуку), тобто Haiku в `claude -p` схильна шукати відповідь в інтернеті раніше, ніж дивитися на список навичок.

## Обмеження процесу

- Baseline знято по одному прогону на сценарій; поведінка моделі між прогонами непослідовна (це саме по собі — аргумент за навичку), тому числа baseline ілюстративні.
- Під час baseline B і D виконувались одночасно з однієї IP-адреси, що могло збільшити кількість 429.
- Перший прогін B на Haiku виконано на офлайн-кеші (у середовищі тієї сесії не було доступу до Wikimedia); прогони в Claude Code desktop — на живих даних.
- Прогони A і B з навичкою — по одному, з явним викликом навички; після виправлень їх ще не повторено, як і прогони без навички на Haiku і сценарії C, D, E.
- Claude Code скорочує описи навичок, коли їх установлено багато; тоді навичку видно лише за назвою, і без явного виклику слабка модель її не знаходить.
- Заміри спрацювання залежать від середовища: той самий опис дав 6 з 24 в одному середовищі і 0 з 24 в іншому, а позитивний контроль — від 1 з 3 до 3 з 3. Порівнювати варто лише заміри з одного середовища одним інструментом.
