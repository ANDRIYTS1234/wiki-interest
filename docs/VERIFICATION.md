# Як створювалась і перевірялась навичка

Навичку зроблено за допомогою AI-агентів (Claude Code), тому головне питання цього документа: як я перевіряв, що зроблене агентом справді працює, а не лише виглядає правильно. Кожне твердження нижче можна перевірити в репозиторії; посилання — на файли й коміти.

## Коротко

1. **Спершу — прогони без навички.** До написання коду я дав сильній моделі три запити з умови й записав, де саме вона помиляється (`evals/baseline/`).
2. **З провалів — вимоги.** Кожну помилку baseline перетворено на вимогу до коду (`docs/SPEC.md`) або на пункт перевірки (`evals/scenarios.yaml`).
3. **Код писав агент, перевіряв я — поетапно.** Кожен етап приймався лише після тестів на записаних відповідях справжнього API і звірки з результатами, отриманими вручну.
4. **Навичку перевірено валідаторами формату, на дешевій моделі і на спрацювання.**
5. **Чесно про межі:** повне порівняння «з навичкою / без» на Haiku для всіх сценаріїв ще попереду; що саме зроблено, а що ні — в останньому розділі.

## 1. Baseline: що робить сильна модель без навички

Перед створенням навички я прогнав три сценарії з умови (A — астрономія, uk; B — інтервальне голодування, pl vs cs; D — шахи, de/es/pt з хибною передумовою) у Claude Code на Opus 5.5 з порожньою пісочницею, без нашої навички. Для кожного — протокол: що агент зробив, де помилився, що виправилось після зауважень рецензента (`evals/baseline/A-astronomy.md`, `B-fasting.md`, `D-chess.md`, коміти `696797a`, `96320e2`).

Висновок baseline: навіть сильна модель дає правильний **напрям** висновку, але **непідтверджені числа** і мовчазні пропуски. Приклади:

| Провал baseline | Сценарій | Що з ним зроблено |
|---|---|---|
| Ділив суму 33 статей на суму 10 статей і робив висновок «тема стійкіша» | A | Порівняння кошиків лише через індекси з bootstrap-інтервалом; суми різних кошиків код не ділить |
| Не помітив аномальні січень–лютий (боти): −50% замість −37% | A | Детектор аномальних місяців, прапорець `ANOMALY_MONTHS`, результат без них |
| Не підсумовував редиректи й перейменування | A | `resolve` збирає редиректи й журнал перейменувань, `fetch` додає їхні перегляди |
| Взяв редирект «Reglas del ajedrez» замість статті, підмінив відсутню статтю іншою | D | Статуси `redirect_resolved` / `missing`; заміну обирає лише користувач |
| Нові статті (гравці, сайти) давали «зростання з нуля» | D | Панель лише зі статей, що існували до базового періоду |
| Паралельне завантаження → 429 → мовчки неповні дані | A, D | Ліміт частоти, повтори, «неповні дані = помилка з кодом 5» |
| Вписані вручну числа в PDF, одне — неправильно округлене | A | Числа у звіті лише через плейсхолдери з `metrics.json`; валідатор відхиляє будь-яку іншу цифру |
| Апостроф у «Сузір'я» ламав shell | A | Назви статей передаються лише через JSON-файли |

## 2. Від провалів до навички

На основі протоколів я разом з Claude склав контракт коду (`docs/SPEC.md`): кожна вимога там має обґрунтування в baseline. Ключове рішення, яке прямо випливає з baseline: **все, що має одну правильну відповідь, робить код, а не модель** — запити до API, кеш, редиректи, метрики, перевірки стійкості, графіки, верстка. Агенту лишається сформулювати запит, погодити кошик статей з користувачем і написати текст висновку. Це й робить навичку придатною для дешевої моделі: їй не треба правильно рахувати, лише правильно викликати команди й чесно переказати результат.

Далі код писав Claude Code поетапно (етапи 0–4, коміти `d8ac365` … `f902a9b`), а я приймав кожен етап лише після перевірки. Чернетку SKILL.md і `references/` написано після коду, навколо реальних команд (`417d44c`), і потім звірено з кодом (`23c755a`).

## 3. Як я перевіряв результат агента

**Тести на записаних відповідях справжнього API.** `tests/record_fixtures.py` записує реальні відповіді Wikidata / MediaWiki / Pageviews; тести проганяють код на них без мережі. Регресійні кейси з baseline закріплені тестами: uk «Марс» — сторінка неоднозначності; pl інтервальне голодування — статті немає; es «Reglas del ajedrez» — редирект на «Leyes del ajedrez»; uk «Нейтронна зірка» → «Нейтронна зоря» (перейменування 2021).

**Синтетичні ряди з відомою відповіддю.** Для метрик (геометричний індекс, bootstrap, leave-one-out, детектор сплесків, аномальні місяці, нормалізація, формат чисел uk) — ряди, де правильну відповідь пораховано заздалегідь.

**Звірка з ручними результатами на живих даних.** Результати `analyze` для сценаріїв A і B на реальних даних звірено з числами, які baseline-агент отримав після доведення рецензентом (наприклад, A: падіння без аномальних місяців, порівняння з контролем через індекси).

**Детермінованість.** Однакові вхідні дані дають побайтово однаковий `metrics.json` — перевіряється тестом.

**Офлайн end-to-end.** `tests/test_e2e_offline.py`: `analyze → report` на знімку кешу сценарію B, будь-який мережевий виклик = падіння тесту, PDF рівно на одну сторінку.

**CI на трьох ОС.** GitHub Actions: ubuntu / windows / macos × Python 3.10 / 3.12, `uv sync --locked`, усі тести, `doctor` з іншої папки — усі 6 комбінацій зелені.

**Ручна перевірка артефактів.** PDF прикладу B переглянуто очима: одна сторінка, кирилиця й польська діакритика, немає порожніх зон і дубльованих чисел (`examples/B-fasting/out/`).

**Тест синхронності документації з кодом.** `tests/test_skill_docs.py` перевіряє, що таблиця прапорців у `references/interpreting.md` збігається з кодом, а приклади плейсхолдерів мають правильні формати. Під час звірки знайдено реальну помилку: приклад у SKILL.md `{…index_norm:pct}` надрукував би індекс 0,85 як «+85%» замість «−15%».

**Ручний прохід SKILL.md як агент.** Я пройшов інструкцію крок за кроком у порожній папці й навмисно ламав вхід (вписане число, невідомий шлях, задовгий текст, неправильний формат). Знайдено й виправлено баг: валідатор приймав `{…index_norm:pct}`; тепер вимагає `:x` для відношень і `:pct` для змін (коміт `31709a0`).

## 4. Перевірка самої навички інструментами для Agent Skills

| Інструмент | Що перевіряє | Результат |
|---|---|---|
| `skills-ref` / `agentskills validate` (відкритий стандарт) | frontmatter, назва, опис | валідно |
| `claude plugin validate` (Claude Code) | YAML, структура навички | «Validation passed» |
| skill-creator, перевірка спрацювання (`run_eval`) | чи викликає Haiku навичку на релевантний запит і чи мовчить на схожий нерелевантний (`evals/triggers.yaml`, 16 запитів × 3 прогони; сирі результати в `evals/trigger-runs/`) | нерелевантні: 8 з 8 правильно; релевантні: спрацювання в 6 з 24 прогонів — **навичку недовикликано** |

**Перевірка спрацювання.** Інструментом skill-creator (`scripts/run_eval`, модель Claude Haiku 4.5) перевірено 8 запитів, на які навичка має спрацювати, і 8 схожих за словами, на які не має: «що таке інтервальне голодування», «напиши статтю для Вікіпедії», «порівняй Польщу з Чехією в нашому CSV з DAU» тощо. Кожен запит — 3 прогони. На всі нерелевантні запити Haiku жодного разу не викликав навичку. На релевантні — лише в 6 з 24 прогонів (жоден запит не набрав потрібних понад 50%). Друга версія опису, «наполегливіша», як радить skill-creator, дала ще гірше — 1 з 24, тому в SKILL.md лишився початковий опис. Висновок: межу «коли не використовувати» навичка тримає, а недовиклик на Haiku — відкрита проблема. Наступний крок — автоматична оптимізація опису (`skill-creator run_loop`) на більшому наборі запитів (`docs/ROADMAP.md`, етап 1). Частина недовиклику може бути особливістю самого тесту: Haiku в `claude -p` часто відповідає сам або йде в пошук, не дочитуючи список навичок; це треба перевірити й у повному агентному прогоні.

**Прогін навички на Haiku.** Агент на Claude Haiku 4.5 з навичкою пройшов сценарій B (офлайн-кеш, бо в середовищі розробки не було доступу до Wikimedia) включно з повторним запитом «а тепер за останній рік». Механічно все спрацювало: правильний `analysis.json` з позначеним замінником, `fetch` без мережевих запитів, PDF на одну сторінку, валідатор відхилив вписане число й задовгий текст, і модель виправила їх сама; на повторному запиті змінено `analysis.json` і перезапущено аналіз з кешу. Але прогін показав три провали, які йдуть у наступну ітерацію (`docs/ROADMAP.md`, етап 1): модель порівняла польський замінник з чеською статтею напряму, винесла рекомендацію з однієї статті і не відобразила частину прапорців якості у звіті. Висновок: ці правила треба переносити з тексту SKILL.md у код.

## 5. Що ще не зроблено

Чесно, щоб рецензент бачив межі перевірки:

- **Повне порівняння «з навичкою / без» на Haiku для сценаріїв A–E** ще не проведене. Інструмент готовий (`evals/run_agent.py`, OpenRouter, один shell-інструмент, логи в `evals/runs/`); запуск потребує мережі до Wikimedia, якої не було в середовищі розробки.
- **`claude plugin eval`** не використано: навичка ще не запакована як Plugin. Це в плані (`docs/ROADMAP.md`, етап 1).
- **superpowers:writing-skills** не використовувався як інструмент; але baseline-підхід, який він пропонує («спершу зафіксувати провал без навички, потім мінімальна навичка, потім той самий сценарій з нею»), — саме той, яким зроблено цю навичку.
- **`/skill-doctor`** не застосовний: він показує, які навички в бібліотеці займають контекст і не використовуються, а не якість однієї навички.
